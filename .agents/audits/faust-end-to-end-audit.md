# Faust Engine End-to-End Audit

## Goal
The Faust engine (instruments, effects, and compiler) must provide a robust, polyphonic, and real-time safe integration with the WebDAW environment. It must accurately map UI parameters to the DSP nodes, handle chords correctly without artifacts, execute safely without blocking the UI thread, and correctly integrate with the DAW's plugin hosting and parameter scheduling systems.

## Current state
The Faust engine uses `@grame/faustwasm` to lazily compile DSP strings into `IFaustMonoWebAudioNode` (monophonic) audio worklets on the main thread. Faust DSP code is currently embedded as strings inside `builtinDSP.ts` and `proSynthInstruments.ts`. Parameter binding heavily relies on string matching between UI descriptors and the Faust-generated addresses.

## Findings
The engine functions for simple monophonic test cases but falls apart under realistic use (chords) and has fundamentally broken UI parameter bindings for almost all built-in devices.

## Issues

### 1. Critical Bugs
- **Monophonic Synths Used for Polyphonic Chords**
  - **Severity**: Critical
  - **Evidence**: `createFaustNode` uses `FaustMonoDspGenerator`. `scheduleFaustNote` schedules all notes for a track on this single node without voice allocation logic. The Resonance demo sends overlapping chords to them.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/compilerEngine.ts`, `src/modules/Synth/useCases/faustInstrumentScheduler/scheduleFaustNote.ts`
  - **Why it matters**: Overlapping notes overwrite the `freq` and `gate` parameters on a single oscillator, causing violent frequency jumps, rapid arpeggiation, and dropped notes, completely breaking chord playback.
  - **Needed / Fix**: Implement polyphony. Either use `FaustPolyDspGenerator` to create natively polyphonic nodes with internal voice allocation, or implement an external voice allocator that spawns multiple `AudioWorkletNode` instances per instrument.

- **UI Parameter Synchronization is Broken**
  - **Severity**: Critical
  - **Evidence**: `TrackNode.updateParam` checks `worklet.parameters.get(paramId)`. In `builtinDSP.ts`, FM Synth's descriptor uses `/fm_synth/op1_ratio`, but Faust compiles it to `/FM_Synth/op1_ratio`. 
  - **Files**: `src/modules/Plugin/useCases/faustEngine/builtinDSP.ts`, `src/modules/Synth/useCases/proSynthInstruments.ts`, `src/modules/AudioEngine/engine/TrackNode.ts`
  - **Why it matters**: Changing any parameter on a Faust instrument/effect UI does absolutely nothing. The engine silently drops the parameter update because the paths don't exactly match.
  - **Needed / Fix**: Update all Faust descriptors in `builtinDSP.ts` and `proSynthInstruments.ts` to exactly match the parameter paths generated by the Faust compiler (including casing and processor name formatting).

### 2. Functional Issues
- **Fake UI Sliders for Eliminated Parameters**
  - **Severity**: High
  - **Evidence**: `Zita-Rev1` in `builtinDSP.ts` hardcodes `rdel = 60;` in a `with {}` block. `Tape Delay` lists `wow_flutter` in its UI descriptor, but the DSP string doesn't implement it.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/builtinDSP.ts`
  - **Why it matters**: Exposes UI sliders that correspond to nothing in the DSP, deceiving the user and failing to apply the intended audio effects.
  - **Needed / Fix**: Replace hardcoded values in `with {}` blocks with `hslider()` definitions, and remove UI descriptors for unimplemented parameters.

- **Fragile Scheduler Fallback**
  - **Severity**: Medium
  - **Evidence**: `TrackNode.ts:459` does `key.endsWith('/' + paramId)` because `scheduleFaustNote` hardcodes short names like `'freq'` instead of providing full parameter paths.
  - **Files**: `src/modules/AudioEngine/engine/TrackNode.ts`, `src/modules/Synth/useCases/faustInstrumentScheduler/scheduleFaustNote.ts`
  - **Why it matters**: If multiple parameters end in `/freq`, the engine will apply the automation or note scheduling to the wrong parameter unpredictably.
  - **Needed / Fix**: `scheduleFaustNote` should resolve and pass the exact full parameter address (e.g. `/FM_Synth/freq`) rather than relying on `endsWith`.

### 3. UX/UI Issues
- **DSP Embedded in TypeScript Strings**
  - **Severity**: Low
  - **Evidence**: Huge template literals in `builtinDSP.ts` and `proSynthInstruments.ts`.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/builtinDSP.ts`, `src/modules/Synth/useCases/proSynthInstruments.ts`
  - **Why it matters**: Breaks syntax highlighting, linting, and formatting for Faust DSP code, drastically reducing maintainability.
  - **Needed / Fix**: Move the DSP code into individual `.dsp` files (e.g., `src/modules/Plugin/assets/faust/`) and import them using Vite's `?raw` suffix.

### 4. Structural/Code Health Issues
- **Initialization Race Conditions**
  - **Severity**: High
  - **Evidence**: `setTimeout(r, 20)` inside the `catch` block of `createFaustNode` in `compilerEngine.ts`.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/compilerEngine.ts`
  - **Why it matters**: Hacky workaround for `faustwasm` library races. On slower machines, 20ms is not enough, causing the plugin instantiation to fail completely.
  - **Needed / Fix**: Replace the hardcoded timeout with a polling mechanism with exponential backoff, or refactor to correctly wait for the `AudioWorkletGlobalScope` module evaluation.

### 5. Performance Concerns
- **Main-Thread Faust Compilation**
  - **Severity**: High
  - **Evidence**: `compileFaustDSP` runs `await generator.compile(compiler, ...)` without offloading to a WebWorker.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/compilerEngine.ts`
  - **Why it matters**: The synchronous C++ -> WASM compilation blocks the main UI thread for up to 100ms per plugin, causing severe jank during project load or plugin instantiation.
  - **Needed / Fix**: Move `FaustCompiler` to a dedicated WebWorker. Send the DSP string, compile in the background, and return the WASM module to the main thread.

### 6. Security/Stability Risks
- **Dead Code Accumulation**
  - **Severity**: Low
  - **Evidence**: `compileAllFaustModules` is exported but never used in the application.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/compilerEngine.ts`
  - **Why it matters**: Increases bundle size and cognitive load unnecessarily.
  - **Needed / Fix**: Remove the `compileAllFaustModules` function.

### 7. Missing Features or Unfinished Integrations
- **Sample Rate Hardcoding in DSP**
  - **Severity**: Medium
  - **Evidence**: `fsmax = 48000;` in the `Zita-Rev1` DSP string.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/builtinDSP.ts`
  - **Why it matters**: If a user's audio interface operates at 44.1kHz or 96kHz, reverbs and delays will have mathematically incorrect decay/delay timings.
  - **Needed / Fix**: Use the `ma.SR` variable provided by `stdfaust.lib` instead of hardcoding `fsmax = 48000;`.

### 8. Low-Effort/High-Impact Improvements
- Fixing the UI parameter paths (Issue 1.2) is extremely low effort (string replacements in the descriptors) but instantly restores all UI control functionality for Faust plugins.
- Removing hardcoded constants from `with {}` blocks (Issue 2.1) immediately restores missing features (e.g., Zita Reverb tuning) to the users.

### 9. Recommended Refactors
- **Extract DSP Code**: Extract the massive string blocks out of TypeScript files into proper `.dsp` files.
- **Workerize Compiler**: The `compilerEngine.ts` module should be refactored to act as a client to a `faust.worker.ts` so the heavy `@grame/faustwasm` compiler library operates completely off the main thread.

## Priorities
1. **Monophonic Chords Bug (1.1)**: Fix immediately to restore playback for demo projects.
2. **Broken UI Parameters (1.2)**: Fix descriptor strings so user controls work.
3. **Fake UI Sliders (2.1)**: Expose DSP parameters correctly.
4. **Initialization Race Conditions (4.1)**: Fix the `setTimeout(20)` logic to ensure stable loads.
5. **Main-Thread Compilation (5.1)**: WebWorker integration to eliminate UI freezes.
6. **Extract DSP (3.1)**: Move to `.dsp` files for better maintainability.
