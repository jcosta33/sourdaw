# Faust Engine End-to-End Audit

## Goal
The Faust engine (instruments, effects, and compiler) must provide a robust, polyphonic, and real-time safe integration with the WebDAW environment. It must accurately map UI parameters to the DSP nodes, handle chords correctly without artifacts, execute safely without blocking the UI thread, and correctly integrate with the DAW's plugin hosting and parameter scheduling systems.

## Current state
The Faust engine uses `@grame/faustwasm` to lazily compile DSP strings into `IFaustMonoWebAudioNode` (monophonic) audio worklets on the main thread. Faust DSP code is currently embedded as strings inside `builtinDSP.ts` and `proSynthInstruments.ts`. Parameter binding heavily relies on string matching between UI descriptors and the Faust-generated addresses.

## Findings
The engine works for simple monophonic cases but breaks down under chords (single mono node). Parameter paths often mismatch compiler output (`/fm_synth` vs `/FM_Synth`). **Teardown** disconnects Faust nodes but never invokes a Faust WASM teardown API. **Inspector** uses rich static descriptors when `getBuiltinPlugins()` matches the device; when it does not, **`deriveParamsFromValues`** fabricates ranges from regex on **parameter id strings**, and **`FaustInstrumentLayout`** further groups params by **name regex** — so `FaustParamDescriptor` / registry metadata is not consistently wired end-to-end. `TrackNode` contains **faust-** special cases instead of routing solely through WAM host abstractions.

## Issues

### 1. Critical Bugs
- **WASM / Faust teardown not invoked**
  - **Severity**: Critical
  - **Evidence**: `TrackNode.removeDevice` calls `destroy()` on Fermenter/Toaster/Levain/GrandBoule, then `for (const n of dn.nodes) { n.disconnect(); }` only — **no** call to Faust’s **`destroy()`**. `unloadWAMPlugin` only `disconnect()` + map delete. `FaustDeviceStrategy` has no lifecycle. **`@grame/faustwasm@0.16.1`**: `FaustAudioWorkletNode` declares **`destroy(): void`** (`node_modules/.../faustwasm/dist/esm/index.d.ts` ~1521); `FaustMonoAudioWorkletNode` extends it.
  - **Files**: `TrackNode.ts` (~349–377), `unloadWAMPlugin.ts`, `FaustDeviceStrategy.ts`, `renderOffline.ts`
  - **Why it matters**: Skipping `destroy()` on Faust worklet nodes may leave WASM/C++ DSP instances allocated until GC; repeated add/remove can grow memory.
  - **Needed / Fix**: Call `destroy()` on Faust worklet nodes when removing devices / unloading WAM / after offline graph teardown (cast or narrow type safely); verify with Pass 5 checklist.

- **Monophonic Synths Used for Polyphonic Chords**
  - **Severity**: Critical
  - **Evidence**: `createFaustNode` uses `FaustMonoDspGenerator`. `scheduleFaustNote` schedules all notes for a track on this single node without voice allocation logic. The Resonance demo sends overlapping chords to them.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/compilerEngine.ts`, `src/modules/Synth/useCases/faustInstrumentScheduler/scheduleFaustNote.ts`
  - **Why it matters**: Overlapping notes overwrite the `freq` and `gate` parameters on a single oscillator, causing violent frequency jumps, rapid arpeggiation, and dropped notes, completely breaking chord playback.
  - **Needed / Fix**: Implement polyphony. Either use `FaustPolyDspGenerator` to create natively polyphonic nodes with internal voice allocation, or implement an external voice allocator that spawns multiple `AudioWorkletNode` instances per instrument.

- **UI Parameter Synchronization is Broken**
  - **Severity**: Critical
  - **Evidence**: `TrackNode.updateParam` checks `worklet.parameters.get(paramId)`. In `builtinDSP.ts`, FM Synth's descriptor uses `/fm_synth/op1_ratio`, but Faust compiles it to `/FM_Synth/op1_ratio`.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/builtinDSP.ts`, `src/modules/Synth/useCases/proSynthInstruments.ts`, `src/modules/AudioEngine/engine/TrackNode.ts`
  - **Why it matters**: Changing any parameter on a Faust instrument/effect UI does absolutely nothing. The engine silently drops the parameter update because the paths don't exactly match.
  - **Needed / Fix**: Update all Faust descriptors to exactly match the parameter paths generated by the Faust compiler (including casing and processor name formatting).

- **Inspector bypasses `FaustParamDescriptor` when plugin lookup fails**
  - **Severity**: Critical (for affected devices)
  - **Evidence**: `DeviceInspector` sets `parameters = plugin?.parameters ?? deriveParamsFromValues(device)` (`DeviceInspector.tsx` ~85–86). **`deriveParamsFromValues`** (~22–73) infers `min`/`max`/`unit` from **regex on parameter ids** (e.g. `gain|volume|level`). When a match is found in `getBuiltinPlugins()`, static lists from `pluginDescriptors` (e.g. `faustEffectDescriptors.ts`) supply proper metadata. **`FaustInstrumentLayout`** does not read `parameterValues` directly; it receives `parameters` and **`categorizeParams`** matches **`p.name`** with category regexes (`FaustInstrumentLayout.tsx` ~21–58) — still orthogonal to compiler-true addresses and log laws unless `parameters` came from a full descriptor.
  - **Files**: `DeviceInspector.tsx`, `FaustInstrumentLayout.tsx`, `Arrangement/models/pluginDescriptors/*`
  - **Why it matters**: Dynamic Faust devices or failed plugin id resolution fall back to heuristics; ranges/scaling can be wrong vs compiled Faust UI.
  - **Needed / Fix**: Always resolve `FaustParamDescriptor[]` from `registerFaustDSP` / module registry by `device.type`, merge with `parameterValues`, and pass through to Inspector; avoid `deriveParamsFromValues` for known Faust modules.

### 2. Functional Issues
- **Fake UI Sliders for Eliminated Parameters**
  - **Severity**: High
  - **Evidence**: `Zita-Rev1` in `builtinDSP.ts` hardcodes `rdel = 60;` in a `with {}` block. `Tape Delay` lists `wow_flutter` in its UI descriptor, but the DSP string doesn't implement it.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/builtinDSP.ts`
  - **Why it matters**: Exposes UI sliders that correspond to nothing in the DSP, deceiving the user and failing to apply the intended audio effects.
  - **Needed / Fix**: Replace hardcoded values in `with {}` blocks with `hslider()` definitions, and remove UI descriptors for unimplemented parameters.

- **Fragile Scheduler Fallback**
  - **Severity**: Medium
  - **Evidence**: `TrackNode.ts:459` does `key.endsWith('/' + paramId)` because `scheduleFaustNote` hardcodes short names like `'freq'` instead of providing full parameter paths.
  - **Files**: `src/modules/AudioEngine/engine/TrackNode.ts`, `src/modules/Synth/useCases/faustInstrumentScheduler/scheduleFaustNote.ts`
  - **Why it matters**: If multiple parameters end in `/freq`, the engine will apply the automation or note scheduling to the wrong parameter unpredictably.
  - **Needed / Fix**: `scheduleFaustNote` should resolve and pass the exact full parameter address (e.g. `/FM_Synth/freq`) rather than relying on `endsWith`.

### 3. Structural/Code Health Issues
- **Architecture Violation: Leaky Abstraction in Audio Engine**
  - **Severity**: High
  - **Evidence**: `TrackNode.ts` intercepts parameter updates explicitly checking `if (dn.type.startsWith('faust-'))`, ignoring the `wamPluginHost` parameter synchronization abstractions.
  - **Files**: `src/modules/AudioEngine/engine/TrackNode.ts`, `src/modules/AudioEngine/repositories/deviceStrategy/FaustDeviceStrategy.ts`
  - **Why it matters**: Violates plugin abstraction boundaries (`plugin-hosting` SKILL). The core audio engine should not contain hardcoded logic for specific plugin formats.
  - **Needed / Fix**: Route all Faust parameter scheduling through standard WAM host parameter interfaces.

- **Initialization Race Conditions**
  - **Severity**: High
  - **Evidence**: `setTimeout(r, 20)` inside the `catch` block of `createFaustNode` in `compilerEngine.ts`.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/compilerEngine.ts`
  - **Why it matters**: Hacky workaround for `faustwasm` library races. On slower machines, 20ms is not enough, causing the plugin instantiation to fail completely.
  - **Needed / Fix**: Replace the hardcoded timeout with a polling mechanism with exponential backoff, or refactor to correctly wait for the `AudioWorkletGlobalScope` module evaluation.

### 4. Performance Concerns
- **Main-Thread Faust Compilation**
  - **Severity**: High
  - **Evidence**: `compileFaustDSP` runs `await generator.compile(compiler, ...)` without offloading to a WebWorker.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/compilerEngine.ts`
  - **Why it matters**: The synchronous C++ -> WASM compilation blocks the main UI thread for up to 100ms per plugin, causing severe jank during project load or plugin instantiation.
  - **Needed / Fix**: Move `FaustCompiler` to a dedicated WebWorker.

### 5. Missing Features or Test Gaps
- **Superficial Test Coverage**
  - **Severity**: High
  - **Evidence**: `__tests__/compilerEngine.spec.ts` consists solely of `it('should export ...')`.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/__tests__/compilerEngine.spec.ts`
  - **Why it matters**: Zero behavioral coverage for the core Faust compiler instantiation, module caching, and node creation logic.
  - **Needed / Fix**: Write actual behavioral tests simulating `faustwasm` C++ instantiation and caching.

- **Sample Rate Hardcoding in DSP**
  - **Severity**: Medium
  - **Evidence**: `fsmax = 48000;` in the `Zita-Rev1` DSP string.
  - **Files**: `src/modules/Plugin/useCases/faustEngine/builtinDSP.ts`
  - **Why it matters**: If a user's audio interface operates at 44.1kHz or 96kHz, reverbs and delays will have mathematically incorrect decay/delay timings.
  - **Needed / Fix**: Use the `ma.SR` variable provided by `stdfaust.lib` instead of hardcoding `fsmax = 48000;`.

### 6. UX/UI & Code Hygiene
- **DSP Embedded in TypeScript Strings**
  - **Severity**: Low
  - **Why it matters**: Breaks syntax highlighting, linting, and formatting for Faust DSP code.
  - **Needed / Fix**: Move the DSP code into individual `.dsp` files.

- **Dead Code Accumulation**
  - **Severity**: Low
  - **Evidence**: `compileAllFaustModules` is exported but never used.

## Priorities
1. **WASM Memory Leaks**: Fix immediately to prevent crashes during playback and offline arrangement rendering.
2. **Monophonic Chords Bug**: Fix to restore playback functionality for chords in demo projects.
3. **Broken UI Parameters**: Fix descriptor strings so user controls work again.
4. **UI Descriptors Ignored by UI**: Feed the `FaustParamDescriptor` array into the UI instead of regex-guessing.
5. **Initialization Race Conditions**: Fix the `setTimeout(20)` logic to ensure stable device loads.
6. **Architecture Violations**: Refactor `TrackNode.ts` to respect `wamPluginHost` abstraction boundaries.
7. **Superficial Test Coverage**: Write meaningful unit tests for the compiler engine.
8. **Main-Thread Compilation**: Implement WebWorker compilation to eliminate UI freezes.
9. **Fake UI Sliders**: Expose DSP parameters correctly.
10. **Extract DSP**: Move to `.dsp` files for better maintainability.
