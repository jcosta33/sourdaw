# AiRuntime module — Agent Guidelines

LLM orchestration, provider routing (WebLLM vs hosted cloud), prompt planning into executable DAW action graphs, agent saga lifecycles, and voice input routing; does not own audio DSP, local neural model artifact storage (BrowserAi), or pattern generation algorithms (AiGeneration).

## Key Subsystems

- **LLM Provider Routing**: Selects between in-browser WebLLM (WebGPU-backed) and hosted cloud providers, handling streaming token generation and schema-constrained tool-calling.
- **Action Planning Kernel**: Decomposes natural language requests into typed `ActionCommandGraph` nodes and compiles them into atomic `Command` batches.
- **Agent Saga Engine**: Manages autonomous agent execution runs, approval bindings, interrupted run recovery, and compensation steps.
- **Voice Ingestion**: Routes speech recognition transcripts through draft admission gates before submission to the action planner.
- **Catalog Audition**: `useCases/agentCatalogAudition/` hears a sample-library candidate and places it. The audition decodes into a buffer it alone holds — never into `audioBufferCache` — measures it through AudioAnalysis, and writes no project state; applying it re-resolves and re-decodes the candidate, refuses audio whose content address is not the audited one, and reaches the project only through one `addClip` command.
- **Domain Previews**: `useCases/agentDomainPreview/` shows a proposal before it lands. Which domains a batch touches — MIDI overlay, audio audition, automation curve, device graph — is read from Command's per-operation effect declaration: the dimension a domain owns, plus the objects the operation creates or removes. A `conditional` dimension does not count — it names a write that depends on live execution-time state an isolated preview never exercises, and the conditionals that do write content are carried by the created and removed objects. This module keeps no second list of operation names, which would drift out of that contract silently; the one membership no dimension expresses is `addClip`, which places audio and MIDI through the same `arrangement` write and is read from its payload. Each touched domain is answered by its owner's adapter reading the isolated projection, and the handle it returns is data: notes, points, buffer measurements, node ids and an edge count, never a project, CRDT or store write. An owner that cannot preview returns a typed `unsupported` result naming the reason instead of an approximation, and `compileAgentRiskApproval` derives that set from the envelope so the risk policy escalates the batch to explicit confirmation: a change nobody can inspect is never direct-committed.

## Invariants & Traps

- AI actions must always compile to versioned `Command` envelopes and execute via `executeAppActionBatch` — direct store mutations from LLM runners bypass undo history and CRDT replication.
- Cloud API keys and authentication tokens are local configuration only and must never be serialized into project documents or synced across collaboration channels.
- Guarded agent execution modes require explicit user approval bindings before high-risk actions (file deletion, track deletion, destructive overwrite) are committed.
- The telemetry projection of an agent run carries no free text the run holds — only identifiers, enum literals, revisions and counts — while the developer-diagnostics projection carries the request, plan step descriptions, decision reason, error messages and cancellation reason only after secret redaction and only when the caller requests project content; plan and artifact summaries reach neither projection.
- A request that names no object still compiles, through the plan-created object route: grounding admits a call whose whole effect lands inside an object the same batch creates, in place of the prompt-vocabulary evidence such an object can never carry. Membership is by what a command changes, not by what it targets — `PLAN_CREATED_OBJECT_COMMANDS` is stated explicitly for that reason, and a command that merely accepts a batch-local target reaches the surrounding project through it. Creation evidence is read from the user request text alone; feeding project data to that reader lets a stored name buy a waiver the user never asked for.
- Declining is a contract, not a free-text refusal. `clarify` must carry at least one question, and `unsupported` stands only when the run already searched the command index successfully — what the outcome reports is that search, never that the searched intents were related to the request.
- An `answer` outcome is a reply, never a decline and never a proposal. The planner produces it only through the terminal `answer.respond` call, which the loop admits alone in its turn, with non-blank text, and with every cited call id resolved, once each, against a successful receipt of the same run; anything else is refused like a malformed decline. Every caller reads the outcome kind before the action list, so a batch beside an answer never runs. The chat shows it as an ordinary assistant message with no `error`, lists the receipts it rests on in a collapsed evidence block, creates no pending confirmation, and completes the run, on a decision resume as on a first turn; the Prompt Bar shows its text as a notice that stays until dismissed and opens the full answer in the chat. Any caller that switches over `PlanningOutcome` handles it explicitly, and the acceptance scorer places it in no frozen class until its corpus is sealed.
- A discovered MIDI transform is a plan item the compiler expands, never a command the runtime executes. It targets one clip — a `$binding` an earlier item produced, or an existing writable MIDI clip — takes no selector and no repeat, and is spliced in place as ordinary `addNotes` commands carrying its own dependencies, so the batch it joins is indistinguishable from one whose notes the provider wrote by hand except in the evidence, which records the transforms expanded. This module owns none of the transform contract and imports no generator ([ADR 0043](../../../.agents/decisions/0043-midi-transforms-compile-to-add-notes-through-the-command-registry.md)).
- A recipe expansion is a compiled preview, never a command the runtime executes. `recipe.expand` reads the recipe catalog and the planning snapshot the transform compiler reads, refuses what a recipe cannot be applied to, and lowers to ordinary `addDevice` and `setDeviceParameter` commands that a later `command.batch.propose` adopts by call id through the same `compiledCallIds` list a transform compilation uses: the loop retains either kind under one reference list, and only the kind says whose revision and provenance an entry carries. Adopted commands are grounded and validated exactly like hand-written items. Each expansion mints its device bindings from a loop-assigned ordinal, so two expansions never collide in one batch. The adopted `{recipeId, title, targetId}` records ride the planned result to the approval snapshot, not compiler evidence, because that evidence exists only for a structured list. A subset re-proposal carries none, since it can no longer say which recipe built what it kept.
- A factory chain preset reaches the planner as a recipe through the same two tools, never through `loadPreset`: `recipe.discover` lists it beside the authored recipes under the same filters, marked by `origin` (authored candidates carry none), and `recipe.expand` lowers it through the one expansion path, its single-value windows yielding the stored values. Discovery withholds a recipe whose expansion would exceed `RECIPE_EXPANSION_MAX_COMMANDS` and warns, so the planner is never offered a candidate the expander refuses. This module holds no preset list or mapping; the owner publishes the recipes ([Arrangement](../Arrangement/AGENTS.md)).
- A measured preview is evidence about one exact batch, never a property of a command. `analysis.measure` with subject `preview` compiles its proposal list and grounds it against the loop's revision as an adopting proposal would, previews it in an isolated workspace, renders and measures the scope in the live project and in that preview, and writes nothing to the live project. The loop retains the measured commands under the call id as a third retained kind beside transform and recipe, under the same `compiledCallIds` list and the same stale-revision refusal. The measurement records the content hash of the batch it rendered, and the figures reach approval only when the batch persisted for approval hashes the same — so a turn that adds any other command, compilation or terminal call beside the preview, or grounding that comes out differently, drops them. They ride the approval snapshot, not the `Command` envelope, and a re-proposal is bound the same way: a subset or changed batch drops them rather than showing deltas for a change nobody measured. The hash leaves out the ids a batch draws for the objects it creates, which every compilation draws afresh, but keeps every supplied literal. The figures are also bound to the live revision the baseline rendered at, so a batch persisted or re-proposed at a later revision carries none. A preview draws nothing from the session's track palette: tracks and buses it creates carry a fixed color, so measuring a change that never runs leaves the next real track's color where it was.
- A planner measurement is spent from its run, bounded before it renders, and local. `analysis.measure` asks the run's admission for one render per target (two for a preview, which renders the live project and the preview) and one reduction per target before anything renders. A refusal is a typed, non-retryable `measurement-budget-exhausted` failure that renders nothing and leaves the loop going, and every outcome settles the reservation to the renders and reductions that actually ran, so a cancel or an early refusal ends at what ran; a caller outside a run has no admission and spends nothing. The measured-seconds and rendered-seconds ceilings and the wall-clock allowance are read from the configured limits on each measurement and arm no run. The allowance is the smaller of the configured ceiling and four times the total seconds all its renders process (its planned render jobs times each render's seconds), floored at ten seconds unless the ceiling is lower; its expiry is a typed `measurement-timed-out`, while a run's own cancel stays `cancelled`. The run is read before each target's reduction. The renders are retained only after every reduction has succeeded, never earlier and never discarded afterwards: retention is content-addressed and evicts the oldest at its limit, so a measurement that stops, times out, is refused or throws must leave the artifact store exactly as it found it. A measurement's own stop reaches its mixdown as that render's `abortSignal`, never as `cancelExport`, because the export cancel flag is process-wide and a musician's export or another mixdown beside it would fail on it. A measurement receipt reaches a hosted provider as figures and artifact descriptors only, never samples, and the request that replays it declares the `measurement` category, which the data policy admits where raw audio, renders and stems stay blocked.
- A user reference is figures in a session store, never audio. `loadAgentReference` lets the user pick one file, decodes it with `decodeAudioFileBuffer` (never the caching decode, so nothing enters `audioBufferCache`), measures it once with the full agent metric set, and keeps only `{referenceId, name, contentAddress, measurements, shape}` in `agentReferenceStore`; the buffer is dropped. The store is outside the project: no CRDT write, no undo, no `executeAppAction`, and it survives a project switch until the user clears it. Each load and each clear takes a new `loadEpoch`, and a load stores only while its epoch is current, so a reference whose load finishes after a clear or a newer load is dropped (`superseded`). `analysis.compareReference` is the planner's only reach for it: it takes `analysis.measure`'s scope, range and metrics and nothing else, renders the project through the same `measureProjectScope` path (same budgets, deadline and revision), and returns `data.kind: 'reference-measurement'` with the reference's figures, each target's project figures and `reference − project` deltas, naming the reference by id and content address and never by file name. It is offered (provider list and catalog) only while a reference is loaded, though the static schema contract and its decision-resume identity always list it; it is excluded from WebLLM; it shares `analysis.measure`'s one-measurement-per-turn slot through `companionToolNames`; its receipt classifies as the `measurement` category, and `reference-audio` stays blocked.
- A chat request reads its thread before it joins it. `readChatThreadContext` collects, from the chat, confirmation, run and AI history stores, the thread's earlier requests, the pending proposal's commands and labels, and the last commit's commands, receipt ids and measured deltas, inside a window of the last `THREAD_CONTEXT_MAX_TURNS` requests, and only for the open project: a confirmation counts by the project identity its command batch records, a direct commit by the identity its chat message was stamped with beside its `agentRunId` and `agentBatchId`. A commit is one batch, counted by its receipt: a confirmation whose batch the run holds a receipt for, whatever status it settled in (a batch that committed with effects pending settles `failed`), or a direct commit, stated by that batch's own receipt and revert group, never by its run's other batches. A confirmation's batch is the one its command batch envelope records, matched to a receipt's work by that envelope's batch id and never by the confirmation's group id: a subset accepted from a larger proposal keeps the replaced proposal's group id but commits, groups its undo entries and receipts under its own batch id. A direct commit takes only the receipt whose work is the batch its message was stamped with as `agentBatchId` once that batch committed a project change: a run can commit several batches directly, the first from the request's message and each later scheduled batch an approving trust ceiling commits from its own, so the newest such message reports its own batch and never another of the run; a message whose confirmations have no receipt reports no commit. A batch that changed no project state is never a commit and never hides an earlier one: Command runs a runtime action (play, stop, seek) alone in its batch, which settles `executed` rather than `committed` and is receipted with no revert group, so its direct message is never stamped with the batch and a confirmation whose executed actions are all `runtime` reports nothing; the thread reads on to the newest project commit. A missing revert group alone says nothing about this — a project batch whose entries carry no group is still a commit, reading `unknown`. A commit carries a `standing` read from the undo history alone, by where `undoHistoryStore` holds its revert group: `standing` in `past` only, `undone` in `future` only, and `unknown` in both (a partial undo or revert), in neither (a later edit empties `future`, the size cap or a cleared history drops `past`) or with no revert group (ungrouped singleton entries). The AI history's panel `reverted` flag plays no part: a panel revert moves the entries to `future` like an undo, and nothing clears the flag after a redo. With no pending proposal and no commit in that window there is no thread state, and the message carries no `thread_context` section and is byte-identical to one built without it. The section is numbers and text, never audio, and each profile fits it under its own `THREAD_CONTEXT_MAX_BYTES` cap, measured in UTF-8 bytes, by whole entries: the newest earlier request, the pending commands, the committed commands and deltas, then the older requests from newest back, stopping at the first that does not fit, so the oldest turns go first. A command whose arguments do not fit is kept by name and label with `argumentsOmitted`. The local cap is part of the local window budget: a five-track receipt turn at the evidence ceiling plus a section at the cap, charged a token a byte, still fits with the reply reserve. Requests ride the `prompt-text` category and commands, labels and receipt ids `project-context`; a hosted request whose section carries measured deltas also declares `measurement`. The run's context evidence records `included.thread` per profile as counts, UTF-8 bytes and the commit's standing only, never thread text. Only the chat passes a thread; the Prompt Bar plans without one.
- A refinement replaces the pending card only by explicit declaration. `command.batch.propose` names the card it refines in `refines`, by the confirmation id the thread's pending proposal carries, never by run id, which a re-preview keeps and a schedule's batches share; no application heuristic retires a card, so a proposal without `refines` leaves the pending card as it was. The planner admits `refines` only when it equals the pending proposal of the thread the request was planned in, refusing it from the Prompt Bar, with nothing pending, and for a batch of a multi-batch schedule, whose replacement would drop the batches still owed; the refusal is an ordinary correctable proposal rejection. A refinement always goes to confirmation, whatever the risk policy would let the same batch do, and preview and plan modes refuse it. Where the replacement persists, the refined card is read again, and one no longer proposed, already replaced or in another project ends the request with that reason and persists nothing. The replacement records the card in `supersedes`; the card is then retired through the same supersession as a re-preview (invalidated, resources discarded, its message saying it was replaced) and its run is cancelled, so it leaves `waiting-for-approval` with its batch cancelled, while the replacement belongs to the refining request's run; once the replacement persists, the request lets go of the chat's Stop before the card retires, so a Stop while it retires cancels neither the replacement nor its run. A retired card shows no Confirm and confirming it anyway is refused as not pending, so the refined change is applied once, through the replacement. The approval view diffs a replacement against the card it supersedes while the store holds it, matching commands by type and the object each acts on, read from the arguments the action registry's mutation identity for that type names, target or not (a send by its track and bus, a parameter by its device and id, a created or automated lane by its track and parameter, a placement by its clip, a marker or section by the id grounding resolved its beat and label to, since the card holds that id in place of those arguments, never by a destination or an insert position, which a replacement may change like a value, a set of members gathered into one object by type alone, and a command acting on a set of sources or placements by the member both sets share when that pairs uniquely, a set of sources also by type alone when it is the only one on each side), and lists each added, removed or changed command with the changed fields' previous and new values, a decibel field at two trimmed decimals, so two values the refinement tells apart look apart (-1.25 dB against -1.3 dB), even where the card's one-decimal action labels round them alike, counting the rest.
- A terse refinement inherits from the card it refines; it never re-reads the provider. An ordinary card — plain commands no compiled list, adopted compilation, creative authority or workflow decided, every one of them naming a target (a non-empty registry target tuple) — carries a `groundingBasis` on its approval snapshot: each request text with the calls it grounded (the first being the request that opened the chain, carried forward through every refinement), each command's full registry target tuple and value form, and every object the chain protects. A card holding any command with an empty target tuple — a creation (`addTrack`, `addMarker`, `createBus`, `addSection`), a marker or section command (`removeMarker`, `setMarkerColor`, `removeSection`, `renameSection`) or `setTempo` — carries none, since the target tuple is the only thing a call continues a pending command by, and refines against its stored batch as below. Grounding a refinement against a basis first grounds the batch in the refinement text alone, as any request, unless a clause states a comparative beside its figure; only when that fails, or such a clause stands, does a call continue the one pending command of its type and exact target tuple — re-reading that command's target from the text that granted it in the live project and changing at most the value one refinement clause binds, among the pending commands the refinement keeps. Such a batch takes that route even when no call continues a pending command, so every value clause beside it is still read against the card ("make Keys 2 dB quieter, less" asks how much less). A batch with two calls of the type and target tuple one pending command alone takes would change that command twice and is refused before either route ("turn Vocals down 1 dB" as two -1 dB cuts). The refinement is read in one fixed clause grammar, and anything outside it is asked rather than guessed: its removals, negations and clause combination are read before either route, and a value clause's shape and vocabulary wherever a call inherits a pending command. Its clauses are the shared splitter's — cut at a comma, semicolon, newline or full stop and at `and`, `but`, `then` or `and then` between clauses — with a trailing `except`/`without` phrase cut off as a clause of its own, and every clause is exactly one of seven kinds. Before any clause is read, a clause of any kind holding a symbol or punctuation mark outside object names (quoted or not) that is none of a figure's own decimal mark, its percent sign, a sign the value reading reads, or an apostrophe inside a word is asked, since the mark may withdraw, negate or qualify what the clause states ("mute Bass ❌", "turn Vocals down 🔇", "remove the snare 🚫", "turn Vocals down 1.5 dB!"); the separators are the splitter's, so "turn Vocals down 1.5 dB." still binds. (1) Filler, a clause that is exactly one entry of one closed list (`please`, `thanks`, `thank you`, `thanks a lot`, `cheers`, `ok`, `okay`, `instead`, `go ahead`, `actually`, `hmm`, `well`, `sure`, `yes`, `yeah`, `hey`, `looks good`, `sounds good`, `great`, `perfect`, `nice`), which is consumed, or a protection, which one closed reader decides by what it names. A protection is a clause in one of a closed set of forms, each stating its slot once (`keep the Drum Bus unchanged`, `leave the Drum Bus as proposed`, `leaving the Drum Bus alone`, `with the Drum Bus unchanged`, `the Drum Bus stays as is`, `no changes to the Drum Bus`), or a closed phrase for the rest of the mix (`everything else`, `the rest`, `nothing else should change`, `keep everything else`); no other clause is read as one, whatever protection words it holds. Naming the rest of the mix it protects nothing and is consumed, unless the refinement also holds an addition, which (5) then asks. Naming one or more project objects, each in whole, by a name denoting that object alone, with no operation word, and none of them acted on by a pending command, it is consumed and protects each object through the chain exactly as the original request's `unchanged` does, so the batch or a later refinement changing one is refused. Naming anything else — a pending object (one the refinement removes included), an operation (`the snare gain`), a name several objects share, `it`, `everything`, or a slot naming nothing — it is asked, never consumed, so a protection cannot keep a pending change the batch drops or changes. A slot may list objects joined by `and` or commas (`leaving the Drum Bus and Bass unchanged`), one protection of each: the clauses the splitter cut there are rejoined only when the text joined across nothing but those separators is exactly one closed form whose slot is a list of whole object names. `leave <object> alone` naming a pending object stays the removal (3) reads. A protection may close on one closed word or phrase, `please`, `thanks`, `thank you` or `instead`, read off its end as `please` is read off a clause's start ("leave the Drum Bus unchanged please"); the clause is read whole first, so an object whose name ends in one keeps its name, and only one is read off. Wherever a call inherits a pending command, no other clause is read as saying nothing: one naming nothing and stating no figure outside that list ("hi", "slower", "wider", "gentler", "double it", "undo that", "unmuted", "toggle it") is an addition a batch must answer, so beside a batch that only continues pending commands it is refused, as unanswered or as a changed value no clause states, rather than ignored. Only beside a batch the refinement text grounded whole by itself, where no call inherits, is a clause of courtesy also consumed, and only when its words outside object names are exactly one entry of a second closed list of greetings, apologies, acknowledgements, thanks and hedges ("Hi", "Sorry", "Thank you very much", "That's all", "if possible"). Courtesy is never read by the words a clause lacks: any other clause there, a retraction or qualifier above all ("No wait", "actually no", "oops", "scratch that", "twice", "slightly"), may withdraw or change what stands beside it, so it is an addition the batch must answer and is refused. (2) A comparative of its own (`less`, `a bit more`); `less` and `more` are read nowhere else. (3) A removal: a removal verb and its <object>, `leave <object> alone`, a bare <object> in the clause right after a removal verb's, which continues it ("remove the guitar pan and the vocal gain"), or the one negation form `not`/`except`/`except for`/`without` [the] <object> [operation word: `gain`, `level`, `volume`, `fader`, `pan`, `panning`, `mute`, `solo`, `arm`], which removes that pending object's changes and protects the object, or after an operation word removes only that operation's changes, or, naming a project object off the card, protects it — except that a negation or a `leave`/`leaving <object> alone` right before or after a removal clause ("remove the snare but not the drum bus", "remove snare except snare bottom", "not the drum bus, remove the snare", "remove the snare, leave the bass alone", "leave the bass alone, remove the snare") is asked, since it may narrow that removal or keep another change, and so is an `except`, `without`, `not` or `but not` naming a project object right after a protection or a rest-of-mix clause ("keep everything else unchanged except the snare", "leaving the drum bus unchanged, except the snare", "keep everything else unchanged, not the snare"), which may carve that object out of the protection, leaving its pending change, or remove that change; a removal names its object by the full name it states first, and reads a trailing generic noun (`track`, `channel`, `bus`, `change`, `one`) or operation word off only when that full name names nothing, so "leave Drum Bus alone" names a track called Drum Bus and "drop Bass Mute" a track called Bass Mute. The removal verbs are one list, `remove`, `drop`, `omit`, `exclude`, `skip`, `leave out` and `take out`, which the stored-card check below reads too; a removal verb opens its clause after nothing but the fixed openers `please`, `can you`, `could you`, `would you`, `you can`, `actually`, `also`, `and`, `then`, `just`, `now`, `ok`, `okay`, `let's`, `let us`, `we should`, `we can`, `instead`, `yes`, `I want you to`, `I'd like you to`, `I want to` and `I'd like to`, any number in any order ("could you please remove"), none spanning an `and`, where the splitter cuts ("go ahead and remove" reaches the verb in a clause of its own); the list is closed, each opener asking for the removal or only softening it, so any other word before the verb ("don't", "you can't", "no need to") removes nothing, and in a clause stating a figure it changes a level instead ("drop the Vocals gain to -1 dB", "drop the Vocals level by 1 dB"). (4) Any other negation — `not`, `never`, `without`, `except`, `cannot` or a verb with `n't` anywhere outside object names ("don't raise Snare", "never boost Snare", "do not change the snare", "not the snare at 2 dB") — which is asked, unless it names no project object, states no figure and states no pending command's operation word (`gain`, `level`, `volume`, `fader`, `pan`, `mute`, `solo`, `arm`) in its own, -ing or -ed form ("not too loud", "without changing anything else"; "don't arm", "arm Bass without muting", "not armed" ask, since each may withdraw that pending change): that one is left alone, and asked only beside a removal, which it may withdraw ("remove the snare, or not", "not the snare, not sure"), a value the refinement binds, a comparative of its own or, on either route, a pending value the batch changes ("turn Vocals down 4 dB, never mind" against a pending 3 dB cut). (5) An addition: a clause naming any object no pending command acts on, where every object text the reference masking hides counts — a VCA group, track, device, device parameter or clip, by its id or its name, and a name of symbols alone ("🎤") by its raw text — grounded in its own clause's text and never bound to a pending command ("turn Drums down 2 dB" for a VCA group named Drums never moves the pending Vocals). An addition, or any clause taking an action no pending command takes on the objects it names ("mute Keys" beside a pending Reverb mix on Keys, which the card's Keys owns), holding a restriction or replacement word (`only`, `just`, `alone`, `instead`, `exclusively`, `rather`, `solely`, `merely`, `simply`, `strictly`, `purely`, `afresh`, `anew`, `in [its] place`, `on its own`, `by itself`, `as a replacement`, `replace`, `from scratch`), or standing beside a clause that is exactly `instead` or beside any rest-of-mix clause (`nothing else`, `no other changes`, `keep everything else unchanged`, `the rest as is`), is asked before either route, as a restatement in such words is, since it may mean the pending changes go and only the addition stays ("mute Bass instead", "mute Bass, instead", "turn Snare down 2 dB only", "mute Bass on its own", "mute Keys and nothing else", "mute Bass, nothing else"); a rest-of-mix clause beside only restatements, value clauses and removals keeps its meaning. (6) A restatement: a clause with no figure naming pending objects, whose words, object names masked, are exactly each pending command's own action words plus articles — the words the source clause that grounded it states beside its figure, without the figure's unit and connector ("turn … down" for "turn Vocals down 3 dB", "mute" for "mute Bass"), or exactly one of the action registry's true or false phrases for its toggle ("unmute Bass", "unsolo Bass", "disarm Bass" against a pending mute, solo or arm), which binds that boolean for the one pending command on the object it names, so a call carrying the other value is refused. Its one closing word or phrase, as a protection's, is read off its end before its words are read ("mute Bass and mute Keys please", "unmute Bass thanks"), never one standing before an object name ("mute instead Bass"). Any other word asks: a toggle in other words ("Bass mute off", "mute Bass off", "mute Bass only"), a restriction ("only", "just", "instead of", "rather than", "excluding" and the like), a direction against the pending move or a unit ("turn Vocals up", "turn Vocals down two dB" against a pending cut). A clause naming no object restates a command only in the direction or side it already moves. (7) A value clause. Clauses combine by one rule: a pending command takes its value from at most one clause, so a figure, direction, side, unit or toggle for the same pending command in a second clause asks, in either order and across any separator ("turn Vocals up, make it 2 dB", "turn Vocals up, 2 dB", "Vocals louder. Make it 2 dB"). A value clause binds an inherited value in one shape only — [opening word] [verb] [object or pronoun] [connector] [sign] figure [unit] [direction, side or `wet`] — with exactly one figure, its connector touching the figure or its sign ("put it at the 6 dB", "bring it to a 2 dB cut" ask), no quotation mark anywhere in it (`make it 2 dB "down"` asks), at most one side beside a pan ("pan it right 20 left" asks), no side beside a moving verb (`bring`, `turn`, `move`, `shift`, `nudge`, `push`), with or without `to` ("bring it 10 right", "move it 10 to the right" ask: the figure may land there or move toward it), while beside `make`, `set`, `put` or `change` the side is where the pan lands, and no sign its direction word contradicts ("lower it +2 dB", "raise it -2 dB" ask). Its words are read in a closed vocabulary, never by the words it happens to know: beside its figure, the unit word that figure is read in and the object names the clause states, every word must be a value verb (`make`, `set`, `put`, `turn`, `bring`, `move`, `change`), a pronoun or article (`it`, `its`, `the`, `a`, `them`), a connector (`to`, `at`, `by`), `please`, a conjunction opening the refinement's first clause (`and`, `but`, `then`), a level phrase word any request reads as a direction (`down`, `up`, `drop`, `cut`, `lower`, `reduce`, `attenuate`, `quieter`, `softer`, `boost`, `raise`, `louder`, `higher`, `hotter`), a pan's own words and sides (`pan`, `panning`, `left`, `right`) beside a pan, or `wet` beside a mix. Any other word anywhere in the clause ("negative", "below", "another", "again", "extra", "go") asks, on every path — a landing, a stated direction, a move keeping the pending direction and a plain value alike; so does any symbol or punctuation mark anywhere in the clause outside object names that is none of its decimal mark, its percent sign or a sign this reading reads ("➖", "⁻", "˗", "＋", "make it 2 dB ↑", "make it 2 dB+", "make it 2 dB 🔊"), a direction beside a landing ("bring it down to 2 dB", "bring it down to 50%"), and a negation naming no object ("not less", "not as much") beside a bound value. Two kinds of value bind. A level in dB binds an explicit figure, signed by `minus` or by any dash or minus character (`-`, `–`, `‑`, `−`) touching it or a space before it, `at`/`to` landing and `by`/`up`/`down` moving (a pending absolute level moves from where it was proposed, never from where the fader is now), its direction read by the level phrase words any request is read by, an unsigned figure with no connector keeping the pending form and sign only when no word beside it could state a direction; a comparative beside the figure (`more`, `less`, `quieter`, `louder`, `softer`, `hotter`, `lower`, `higher`; `lower` opening the clause is its verb) is asked against a pending move, which it could replace or add to, and beside a landing, and only moves a pending absolute level. Every other value — a pan, a device parameter, a linear level — binds only an unsigned figure after `to`/`at` or standing bare, in the value's own unit or none: a device parameter's declared unit, a percentage for a pan or a scaled linear level, and otherwise the unit its value argument is named for; a bare figure binds a pan, or any value in a signed range, only beside a side (`left`/`right`). A signed figure (any minus, dash or plus, character or word), a relative one (`by`, `up`, `down`, `more`, `less`, `bigger`, `smaller`, `increase`, `decrease`, a comparative or any other direction word), one in another unit, or a bare one beside a word this reading cannot tell is asked. A unit word reads apart from its figure too ("two dB" states a unit), except the bare `s` a contraction leaves ("that's"), which reads as seconds only directly after a figure. Side and direction words are read only outside the object names the clause states, so a track named "Left Guitar" or "Up Lead" states no side or direction; the unit word the figure is read in (`%`, `percent`, `per cent`, `dB`, `Hz`, `bpm`, `ms` and the like) states no direction, nor does `wet` beside a mix parameter's figure, while `dry`, which would invert it, is asked. The bound value still passes the unit, level-law, direction and range rules, read from that clause. A standalone `less`/`more` clause only checks the bound value against the pending one: against a pending move it asks for a smaller or larger move (the bound magnitude against the pending one), against a pending absolute value for a lower or higher value than the pending one, never against where the target is now, and a value of another form than the pending one has nothing to compare against and is refused; against a pending pan, on either side and either route, it is asked, since it cannot say whether the pan moves toward the centre or further to its side ("less, pan it 40 left" against "pan Bass 30% left"). An addition clause stating an action an intent resolves is answered only by a call of that action, on an object the clause names when it names any, and only one stating no such action ("Bass please") by a call touching an object it names, so "turn Bass down 1 dB and mute Bass" carrying the Bass cut alone leaves "mute Bass" unanswered. Every other call grounds in the text of all the addition clauses it answers, never in the whole refinement, whose other clauses change or keep pending commands ("turn Vocals down 1.5 dB and turn Bass down 1 dB" grounds the Bass cut in its own clause beside the inherited Vocals and Snare), and a call no addition clause answers is refused. Whichever route grounded the batch — the refinement text alone, beside a comparative or not, or inherited calls — its result passes one final check before it is admitted: no pending command the refinement removes is kept, a pending command leaves the batch only through a removal that names it in whole — a call carries at most one pending command, the one of its type and target tuple, or where several share that tuple (two automation points on one lane) the one whose payload it states exactly — and every addition clause is answered by a call continuing no pending command ("mute Bass and mute Keys, and solo Keys" carrying only the two mutes is refused). The chain's protections — each source text's, the card's and what the refinement removed — bind the batch, its scope, its preflight and the card it persists, compared against every object id a command touches: each member of an array target, a device parameter as `deviceId:paramId`, and the track every owned object it names belongs to — a device's, clip's or automation lane's track, the tracks an adjustment layer processes and a VCA group's members. A batch without a basis grounds exactly as before, and a refinement of a card without one is held against the card's stored batch: a command it does not carry exactly pairs by type and the object ids it states — a creation by where it creates and what it names, never by an id the application minted for it (an id the creating command's payload carries and its provider schema does not declare), which every grounding mints afresh, and a creation the application mints no id for at grounding is still a creation (a track named Percussion never pairs with a pending track named Drums, so "add an audio track named Percussion, leaving Drums unchanged" omits it, while restating "add an audio track named Congas and turn Vocals down 2 dB" against a card adding Congas keeps it); a creation that names nothing ("split clip-1 at bar 4", a marker at another beat) pairs only with the same creation under a fresh id — and an unpaired command stands only when the request drops it by the refinement reader's own reading: its clauses cut by the shared splitter, a removal verb from the one list opening its clause after nothing but the fixed openers ("please don't remove", "no need to remove" remove nothing) with no figure in it, removing only when nothing but binding words, object names and the reference trailers the refinement reader reads (`too`, `please`, `thanks`, `thank you`, `as well`, `entirely`, `altogether`, `completely`, `for now`, `from it`, `from the [pending] proposal`, `card`, `change`, `batch`, `list` or `mix`, any number of them; the basis route reads its removals by the same trailers) follows its object and operation word ("remove the Vocal gain from the card please" removes it, "drop the snare gain a bit" keeps it), or a clause right after one that is a bare object name and nothing else — articles, one object name, at most one operation word ("the vocal gain"; "the Vocals gain stays", "vocals fader up" continue nothing) — and every name read whole, longest first, among every project object's name beside the pending target ids and creation names ("remove the Delay 2 from Keys" names the Keys device Delay 2, never a pending Delay), a name that is itself a binding word ("Gain", "Pan") never read as an object. It drops a command by its target and operation — a pan by `pan` or `panning`, a gain by `gain`, `fader` or `level`, a mute by `mute`, a solo by `solo` ("remove the keys solo"), an arm by `arm`, any other by the last word of its type that names no kind of object (`lock` for `lockClip`), never by `track` or `clip`, which name the object it acts on ("drop the Room Mic track mute" keeps a pending Room Mic arm) — every object id it states named, or a creation by the name of what it creates ("remove the compressor") — and then only when that removal picks out exactly this one pending creation, by its name and the host named after it ("remove the compressor from Bass") or by a name no other pending creation shares; a removal picking out none removes nothing, and one naming no host for a name several pending creations share is refused, asking which one. Validators may not import use cases, so `validateRefinedProposalActions` takes that reading as a port, `readStoredCardRemoval`, beside the created-object reader. A creation the request removes is refused when the batch pairs it anyway, as it does when the provider creates it again under a fresh id. A negation (`not`, `except`, `without`) drops nothing from a stored card.

Only a chat request is read this way, and only while the thread holds no pending proposal, whose refinement owns every follow-up: `planLastCommitContinuation` reads the whole request in one closed grammar — an undo (`undo that`, `revert the last change`, `take it back`), a decibel continuation (`another`, `a further` or `an extra` N dB, N dB `more` or `less` [`than that`], or a comparative with no figure), or a re-target (`do the same to` a list of tracks, or that list followed by `too` or `as well`) — around a closed set of openers and closing courtesies, and a request outside it is planned exactly as any request. It works only from a commit whose standing is `standing`, reading the committed commands from that commit's revert group in the undo history, never from the thread text a provider budget may cut; a thread with no commit, an undone commit (a second undo included), a commit of unknown standing and a group the history holds partly as callbacks are refused. A continuation changes only the committed decibel levels of commands that create nothing: a committed move continues as a move from wherever the level is now, by the figure in its own direction for `another` and `more`, and made smaller by it for `less`, which is refused where it would cancel or reverse the move; a committed level continues from that committed value, never from where the fader has moved since, `more` landing higher and `less` lower, while `another` is asked, having no way to go. The compiled batch crosses the validation, state guards, production brief and risk policy every application-compiled batch does. An undo is the `revert` planning outcome, which carries no batch and which the acceptance scorer places in no frozen class until its corpus is sealed: the chat reads the group again when it runs and undoes it, only in a mode and trust ceiling that may commit a reversible change, as one atomic replay through Command's `revertActionGroupAtomically`, the replay `undo()` gives a group: a group no longer applied whole, one holding a member with no inverse command, and one any inverse of which conflicts with the project as it is now (a committed track since removed) undo nothing and are refused with the reason, never left split across the undo history, and a group undone whole is marked reverted in the AI history as the panel's revert marks it.
