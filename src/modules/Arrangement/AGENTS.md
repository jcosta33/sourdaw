# Arrangement module — Agent Guidelines

Owns arrangement tracks, clips, comping/take lanes, markers, sections, VCA groups, adjustment layers, scratch pads, track alternatives, mixer snapshots, solo mode, and device chain topology; does not own audio DSP graph execution (AudioEngine), raw MIDI notes (MIDI), parameter automation curves (Automation), or playback clock transport (Transport).

## Public Contract Surface

Public surface: `useCases/index.ts`, `stores/index.ts`, `events/index.ts`, `presentations/views/index.ts`.

## Key Subsystems

- **Track & Clip Aggregate:** `trackStore` maintains the hierarchical track list (audio, MIDI, bus, folder, return), device chains, and clip placements.
- **Audibility Projection:** `deriveEffectiveAudibility` projects authoritative solo/mute states into per-track audibility maps consumed by the offline renderer and mixer UI without duplicating logic.
- **Solo Mode:** `soloModeStore` holds the session's SIP/AFL/PFL mode beside the solo logic that reads it; live playback and offline render read it from here. `setSoloMode` is its only writer, and `syncSoloModePreference` mirrors the persisted Preferences `soloMode` into it. The store itself is memory-only.
- **Timeline Editing State:** `timelineEditingStore` holds ripple mode, the snap grid, automation lane visibility and the inline automation sub-lanes, beside the ripple planners, the sub-lane hit test and the transient quantizer that read it. `toggleRippleEditing`, `setSnapValue` and `setAutomationSubLanes` are its writers; WorkspaceShell's toolbar and app-action entry points call them and never write the store. The store is memory-only session state.
- **Freeze & Bounce Pipeline:** Tracks offline freeze/bounce state and invalidation staleness (`initStalenessDetection`, `cleanupUnusedFreezeFiles`).
- **Comping & Take Management:** Multi-take slicing and comp region resolution (`resolveClipsWithComping`).
- **Adjustment Layers & Scratch Pad:** Non-destructive bus-level effect overlays and sandbox arrangement sections.

## Invariants & Traps

- **Atomic Mutations & Undo:** Every track, adjustment layer, and clip edit must pass through registered handlers to guarantee undo graph consistency and freeze staleness invalidation.
- **Device Parameter Bounds:** Parameter writes must strictly pass through `clampDeviceParamWrite` and `persistDeviceParam` adhering to `models/DeviceParameterLaw.ts`.
- **Worklet Decoupling:** Worklets and DSP threads do not read `trackStore` directly; AudioEngine consumes immutable live track strip projections (`projectTrackToLiveStrip`).
- **Effective Audibility Single Source:** Never calculate custom solo/mute matrix logic in downstream modules — always consume `deriveEffectiveAudibility`.
- **One Vertical Scroll Range:** `timelineViewStore.scrollY` is the single vertical offset of the track-list headers and the timeline canvas. `setScrollY` clamps it to `getTimelineContentHeight` (visible tracks, each its own row plus the block of variation lanes under it: one `VARIATION_LANE_HEIGHT` row per alternative while the track's lanes are on, never for folder or master rows) minus `viewportHeight`, which only the canvas writes. The header list scrolls the same range because it ends with a spacer sized from the measured scroller height minus `viewportHeight`, which covers whatever sits under the canvas (the horizontal scrollbar strip, which `TIMELINE_HORIZONTAL_SCROLLBAR_HEIGHT` keeps always reserved, and an open scratch pad). `initTimelineScrollClamp` re-clamps `scrollY` whenever the track list changes, so deleting tracks or collapsing a folder never leaves blank canvas. `models/TimelineTrackExtent.ts` is the one row-extent law: the canvas advances by it, every y-to-track mapping (`getTrackAtY`, the hit tests, `resolveTrackAtY`, the marquee) steps by it, and the header list renders exactly that many lane rows under a track, so the two columns agree on every row's top. The track-list scroller is `flex: 1 1 0` with `min-height: 0` so it never contributes content height to the arrangement; the shell floors the arrangement instead (`useArrangementMinimumHeight`).
- **Active Alternative Clips Are `track.clips`:** An alternative's stored `clips` copy is refreshed only when the user switches or creates an alternative, so the active alternative's copy goes stale with every main-row edit. A reader that means what an alternative or a track holds now goes through `models/TrackAlternativeClips.ts` (`getAlternativeClips` for one alternative, `getHeldClips` for every clip a track holds, both exported from `useCases`); the active alternative's contents are `track.clips`, and its stored copy is never counted. A reader of the stored snapshot reads `alternative.clips` directly on purpose: persistence, undo capture and restore, switch/create/delete, clip-id reservation, and the collectors that must keep every stored copy's buffers alive. Nothing syncs the copy on every clip write.
- **Selection Holds Only Existing Clips:** `initClipSelectionReconciliation` subscribes to `trackStore` and drops from `clipSelectionStore` every id no track clip, inactive-alternative clip (drawn in its variation lane, so only while the track shows its lanes) or ghost clip carries, resolving the primary through `resolvePrimaryClip`. Removal routes (undo, collaborator deletes, track deletes, project loads, AI actions) never clear the selection themselves, so do not add per-route pruning; the marquee is a time range and is left alone. The active alternative is read from `track.clips`, never its stored copy, which is refreshed only on a switch. A new selectable clip source must join its existence check.
- **One Musical Range Law:** A section reference, bar range, or beat range becomes beats only through `models/MusicalRange.ts`, read by `resolveMusicalRange` against a caller's snapshot and by `readMusicalRange` against the live project. An exact section name wins; otherwise an ordinal counts among sections of one name family ordered by start. A number written after the name ("Chorus 2") counts only in a family whose names carry no numbers; where they do, it is a name, and one no section bears is unknown rather than a position. Word and suffixed ordinals ("second chorus", "2nd chorus") always count. A reference no section answers is read against markers by the same rules, a marker being a named position whose range runs to the nearest later marker or section start, or else to the arrangement end (`getLastClipEndBeat`'s law, `models/ArrangementEnd.ts`). Two places that match equally are reported as `ambiguous-section` with both candidates and are never picked between, so a planner can ask rather than guess. `section` with `barsBefore` is the N whole bars that end where that section starts, found through `barAtBeat` (the meter map's bar for a beat and whether the beat is its bar line) and `barStartBeat`; a section inside a bar or with fewer than N bars before it is `invalid-range`, never clamped, and a bar range opening at or after the end of an arrangement that holds a clip is `invalid-range` too.
- **Device Selection Metadata:** A descriptor's `characterTags` (the algorithm it runs) and `effectFamily` (the kind of effect it is) are the only way another module selects devices by meaning; callers keep no device-id lists. Both are catalogue metadata, so neither enters the command-replay descriptor version.
- **Presets Published As Recipes:** `getMixRecipeCatalog` returns the authored recipes, then the factory chain presets published as recipes of the same shape, each marked by an `origin` naming its preset and the preset's contract fingerprint (`getPresetContractVersion`, the version the preset discovery manifest also publishes). Only factory presets that are effect chains qualify; user presets and genre or character templates are not published. Each preset device is an `insert` step and each stored parameter a window whose minimum equals its maximum, so applying one writes the stored values through `recipe.expand`'s `addDevice` and `setDeviceParameter`, never through `loadPreset`. Descriptors and roles come only from the preset's authored tags and category through the catalog vocabulary, never from a device's behaviour: a tag names a character the author intended and is not proof of an algorithm (a tube-tagged preset need not run a tube algorithm). A preset whose category and tags name no role is a generic processor, published with no role, which serves any source track. A preset whose tags name no produced descriptor, or holding a device that is not an effect or a value its parameter cannot hold as stored, is not published; a corrective descriptor (`muddy`, `thin`) is never read from a tag, and `controlled` stays with the source-backed authored recipes. `getAddedDeviceParameterValues` reports the values `addDevice` gives a placed device (its plugin's internal values, then each declared parameter's value), read from the same composition `addDevice` writes, so a caller can tell a redundant write without a second copy of that law. Prerequisites, contraindications and metrics stay empty because the catalog defines them per recipe, not per descriptor. The authored catalog arrays and their coverage spec stay authored-only; preset recipes carry their own validation in `buildPresetMixRecipes.spec.ts`.
