# MIDI module — Agent Guidelines

Owns MIDI note data, CC/pitch-bend/articulation events, note transform algorithms (quantize, humanize, transpose, legato), chord track events, groove templates, step recording, and WebMIDI hardware input/MPE routing; does not own clip arrangement placement or track strips (Arrangement) or synth audio DSP (Synth / AudioEngine).

## Public Contract Surface

- `stores/`: `midiStore` (`MidiStoreState`), `grooveTemplateStore` (`GrooveTemplateState`, `GrooveTemplateAssignment`, `GrooveConsumerType`), `grooveTemplateProjectRevisionStore`, `chordTrackStore` (`ChordTrackState`), `stepRecordStore` (`StepRecordState`), `webMidiStore`.
- `useCases/`: Note CRUD (`addMidiNote`, `appendMidiNotes`, `batchAddMidiNotes`, `removeMidiNote`, `moveMidiNote`, `resizeMidiNote`, `setNoteVelocity`, `setNoteProbability`, `getNotesForClip`, `setNotesForClip`, `splitMidiNotesAtBeat`), note transforms (`quantizeNotes`, `quantizeNoteLengths`, `humanizeNotes`, `transposeNotes`, `invertNotes`, `retrogradeNotes`, `legatoNotes`, `scaleVelocities`, `strumNotes`, `snapClipToScale`), clip MIDI data (`duplicateMidiClipData`, `glueMidiClipData`, `prepareMidiClipSplit`), chord track (`addChordEvent`, `removeChordEvent`, `moveChordEvent`, `updateChordEvent`, `createChordPitchProjector`, `getChordAtBeat`, `transposeForChordTrack`), groove templates (`createGrooveTemplate`, `extractGrooveTemplate`, `applyGrooveTemplate`, `assignGrooveTemplate`, `previewGrooveTemplate`, `projectClipMidiEvents`), MIDI events (`addMidiCC`, `addPitchBend`, `setNotePressure`, `setNoteSlide`), step recording (`toggleStepRecording`, `stepRecordNoteOn`, `stepRecordNoteOff`, `stepRecordAdvance`), WebMIDI (`initWebMidi`, `selectMidiInput`, `setMidiInputTrack`, `panicLiveNotes`, `triggerLiveNoteOn`, `triggerLiveNoteOff`, `resolveLiveInputNoteReceiver`), file I/O (`readMidiFile`, `downloadMidiFile`), registry (`MIDI_EFFECT_FACTORIES`).
- `events/`: No public domain event payloads exported.
- `presentations/views/`: No views exported (piano roll UI lives in `TimelineEditor`).
- Handlers: `getChordTrackHandlers()`, `getMidiGrooveHandlers()`, `getMidiNoteTransformHandlers()`, `getPatternInstanceHandlers()`, `getWebMidiInputHandlers()`.

## Key Subsystems

- **Note & Expression Model:** Note start, duration, pitch, velocity, probability, and per-note MPE/expression data stored by clip ID.
- **Note Transformation Engine:** Algorithmic manipulations (quantize, humanize, retrograde, invert, legato, scale, strum).
- **Groove Engine:** Non-destructive groove template extraction, previewing, and live dynamic projection (`projectClipMidiEvents`).
- **Chord Track & Pitch Projector:** Harmonic progression model with dynamic scale/chord pitch conforming (`createChordPitchProjector`).
- **WebMIDI & Step Recording:** Low-latency WebMIDI hardware input with MPE channel routing, panic/all-notes-off, and step sequencer recording.

## Invariants & Traps

- **Relative Clip Coordinates:** Notes in `midiStore` are stored with clip-relative start beats (not absolute arrangement timeline beats).
- **Non-Destructive Grooves:** Groove template application dynamically projects note timing without mutating stored note timestamps unless explicitly committed.
- **Recorded Channel Events:** While recording on an armed track, channel controllers (0..119, raw number and 7-bit value, including RPN/NRPN and data entry) and non-member-channel pitch bend are recorded for the recording clip at the beat and in the clip a note-on at that instant gets (`resolveRecordingPlacement`). Every message is kept in arrival order (the CC lane's `addMidiCC` dedups by beat, channel and controller and is for editing only). Controllers owned by a MIDI-learn mapping and MPE member-channel slide and bend stay out. The rows wait in `recordedControllerTakeState`, not in `midiStore`, because each store write reconciles the clip's whole row list and would stall every flush as the take grows. Each carries the id it will hold in the store. `handleCommitRecording.describe` only reads them (`planRecordedControllers`) into its redo snapshot; `execute` writes them in one store write inside the commit's storage transaction (`commitRecordedControllers`), with no undo entry, so a commit that does not land writes nothing (`discardRecordedControllers` drops the buffer) and a message arriving after the write belongs to no take, unless a later take was already recording into the clip when the write landed (its commit waited behind a snapshot transaction): that take's later rows are an overdub, written when it ends. The commit writes no note list: a MIDI clip's stored controllers play, live, on relocation and in export, whether or not it has a note list (a clip without one plays no notes), so a take of controllers alone is audible and a clip derived by split, copy, duplicate or paste that drops an empty list keeps its controllers. A structural placeholder list is never written for playback's sake, because a peer that records the clip's first note concurrently creates its own list at the same key and the merge can drop one of the two. A clip the recorder did not open (an overdub) flushes when the transport stops recording; a discarded take's buffer is dropped unwritten. A new take's rising edge drops what no commit will claim, but a buffer whose opened clip is still on the timeline and uncommitted survives until its commit. A sustain, sostenuto or soft pedal already held when the take begins (`heldPedalState`, read at the transport's recording rising edge) leads the clip's list at beat 0 on its channel, only while it is engaged by the test `isPedalControllerLift` gives stored playback (a switch pedal below 64 holds nothing), unless the take's first pass records that controller and channel at beat 0 itself (a row at beat 0 arriving after a row later in the clip is a later loop pass and stands in for nothing) or the live route would not record it (`admitsRecordedControlChange` is the one admission rule for both, so a pedal a mapping owns is never seeded). A take that ends with a sustain, sostenuto or soft pedal still engaged (its last planned row for that pedal and channel in beat order, arrival order breaking ties at one beat, is not a lift, by the same test, because a loop take overlays every pass into one clip and playback reads the rows sorted by beat) gets a lift row of value 0 in the same plan, because stored playback plays a lift only from inside the clip or on its closing line and the pedal would otherwise stay down past the clip until the transport stops (Cubase writes reset events at a recorded part's end). It sits on the clip's closing line, for a clip the recorder opened (the lift plays as `closesClip`) and an overdub alike, never at the beat the take stopped: a loop take's stop beat is the wrapped playhead, which can fall before a press still held from late in an earlier pass, and a lift there would cancel it. The lift is part of `planRecordedControllers`, so the redo snapshot and the write carry the same rows, ids included. `heldPedalState` is the physical pedal position, so transport stop, pause and seek leave it standing; only an input-device reset or teardown (`resetInputDeviceControllerState`), a change of the input target track (a pedal pressed under another target never reached this one's instrument), and Reset All Controllers clear it. `MidiPitchBend.value` is the signed 14-bit wire delta (-8192..8191, 0 = centre), the same unit as `MidiNote.pitchBend`. Pitch-bend rows written in the earlier 0..127 lane unit are read in the signed unit without migration, deliberately, because issue #3779 rules out legacy-project compatibility and migrations. Playback and the offline render read the rows as the track's channel bend (`projectChannelBend`, placed by the passes, content offset and carry rule `projectClipControllerEvents` uses; a row on a clip's closing line is dropped and nothing resets the bend at a clip end), and read its depth from the RPN 0 rows the same clip stores (`createStoredBendRangeReader`, which runs the live input's own RPN state machine), else the MIDI 1.0 default of ±2: a range the controller declared before the take began is not in the rows the take records, so the take begins with it (`readBendRangeSeedRows`, read from `channelControllerState` at the rising edge beside the held pedals): each channel whose whole registered-parameter state differs from a fresh channel's, not only its range (a keyboard that left RPN 0 selected at the default range, or with no range at all, still has a Data Entry the take records heard at the range it sets), and which the live route would record (`admitsRecordedControlChange`; an MPE member channel, whose bend is per-note, has none) leads the clip with that channel's registered-parameter state at beat 0 (`declareChannelState`: RPN 0, its data entry, then the selection the keyboard left, the Null RPN included), unconditionally like a held pedal, whether or not the take records a bend, and once, because a carried-over clip keeps the declaration of its own take and a loop pass is no new take; a row the take records itself at beat 0 follows the declaration and overrides it. A take into a clip an earlier take already holds rows in (an overdub into an existing clip, or a take into a carried-over clip, whose buffer begins with the earlier take's rows) has no beat-0 seed there, and the clip reads one state per channel across both takes, so each take's bends and parameter rows replay under the state that was live when that take recorded them only through declarations: when the take ends, `declareOverdubRegisteredState` walks each channel's rows of both takes in the order the clip will hold them (the later take's after the earlier one's at one beat, because the write appends them and the reader sorts stably), tracking each take's own state machine (the earlier take's replayed from its rows, its seed included; the later one's from the state the input held when the take first filed a row into that clip, `registeredStateAtFirstRow` on the clip's buffer, read before that row's own message moved it and not at the rising edge, because one take can overdub several clips and reaches each under whatever the performer has declared by then, advanced by its own rows), and at every beat where the state in force is not that of the take whose bend or RPN, NRPN or Data Entry row sits there, adds `reconcileRegisteredParameterMessages` to the later take's buffered rows at that beat (`interleaveRegisteredStateDeclarations`): ahead of the later take's own rows of the beat, so a declaration it recorded there still wins, and otherwise after the earlier take's rows of the beat, which a bend at that beat reads past. A channel the later take writes no such row to, or where the two states agree at every changeover, gets nothing. A clip cut away from the rows that declared its range keeps the range, because the RPN, NRPN and Data Entry rows (`isRegisteredParameterController`) are messages to a state machine, not lane values, and the last value of each lane (a Null RPN after the data entry it closes) does not say what state they left. A split's right half and a glued source whose window starts after its first rows therefore begin with one ordered declaration per channel (`reconcileRegisteredParameterMessages`: the range through RPN 0, then the selection the channel ended on, the Null RPN included, with its data entry bytes), at the clip's origin, which replays through `applyRegisteredParameterChange` to the state the source was in there; and a glued source that follows another begins with the declaration that returns its channels to its own state (the default range and the Null NRPN when it declared none), because the glued clip reads one state per channel across all its sources. A channel that never selected anything cannot be returned to that, only to the Null NRPN, never the Null RPN: an RPN select over the Null RPN keeps the number's other half, so a take's lone half-select of RPN 0 would miss RPN 0 and its Data Entry would be ignored, while the same select over an NRPN starts the number over, as it does on a channel that never selected. A bend the cut carries onto that origin was read, before the cut, at the beat its row was recorded at, but is an ordinary row on the origin after it, so where its recorded state differs from the declared one its channel also gets, on the origin after the declaration, the reconciliation to the recorded state, and the reconciliation back (`reconcileCarriedBendRanges`), unless a bend or registered-parameter row of the clip's own on that channel plays within the same-beat tolerance of the origin: the reader reads it with the origin's rows, so the carry is replaced, or its state rewritten, at the instant it starts, and the channel keeps the declared state. The return is always written, one sequencer tick after the origin (`carriedBendReturnBeat`, `SEQUENCER_TICK_BEATS` = 1/960 beat), whatever the clip's later rows, so a bend drawn or moved there later reads the state at the cut; it comes earlier, ahead of the row, when the clip's own first row after the origin plays within that tick, and in a glue never past the source's closing line (its end, or the next source's head when that comes first), where the next source's state begins. It cannot share the origin, because the range reader reads one beat's rows, to within the same-beat tolerance, before the bend on it. A point set by hand through `addMidiCC` that changes RPN 0's bend range where it lands (`editSetsBendRangeWhereItLands`: a Data Entry MSB, Data Increment or Data Decrement, with RPN 0 selected when it arrives by the channel's stored rows up to it, in the reader's order) on the origin, or any beat up to one tick before a return, replaces that channel's returns there (`isCarriedBendReturnOnEditedHead`, recognised by their `rpn-after-carried-<n>` ids), because they would re-send the state at the cut over it and the hand-set range would govern no later bend; a select, a Null RPN, a Data Entry LSB, or a Data Entry the state machine ignores (a recorded state that ended on the Null RPN or an NRPN, as a keyboard usually leaves it) sets no range and leaves the returns, so later bends stay at the state at the cut. The CC lane's undo restores the rows the add displaced, returns included, each at its pre-add position in the list (`restoreMidiCCPoints`), because a return pulled onto the beat of the clip's own first row must stay ahead of that row: the reader breaks same-beat ties by list order. A channel that never declared a range steps Data Increment and Decrement from the MIDI 1.0 default of ±2 (`stepBendRange`), live and in the reader alike, so a declared default range and an undeclared one answer the same. A duplicate, a paste, a copy and a flatten fan-out copy the rows whole and a slip or trim moves only the content offset, so none of them loses the state. The other lanes keep the value-in-force carry.
- **Live Note Panic Safety:** `panicLiveNotes` must broadcast note-off messages across all 16 MIDI channels to prevent hanging audio synth voices.
- **Hardware Port Reconnection:** WebMIDI input listeners must handle hot-plugged devices and state teardown gracefully.
