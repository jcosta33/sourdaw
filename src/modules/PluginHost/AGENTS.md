# PluginHost module — Agent Guidelines

Third-party plugin hosting runtime: manages native plugin discovery (VST3, CLAP, AU), desktop IPC bridge, and Faust dynamic DSP JIT compiler.

## Domain Ownership

Owns third-party native audio plugin lifecycle (VST3, CLAP, AU scanning, loading/unloading, native GUI window management, parameter/preset synchronization) and the Faust dynamic DSP JIT compiler. Does not own WebAudio graph nodes or track channel strips (AudioEngine), or device chain models in the arrangement (Arrangement).

## Public Contract Surface

Public surface: `useCases/index.ts`, `stores/index.ts`. The module exports no events or views.

## Key Subsystems

- **`repositories/pluginBridge/`**: Desktop IPC bridge for native plugin host processes (`scanPlugins.ts`, `loadPlugin.ts`, `unloadPlugin.ts`, `openPluginGui.ts`, `closePluginGui.ts`, `setPluginParameter.ts`, `setPluginBypass.ts`, `getPluginState.ts`, `setPluginState.ts`, `readPluginTails.ts`, `onPluginLatencyChanged.ts`, `onPluginServiceChanged.ts`).
- **`stores/`**: `pluginScanStore.ts` (discovered plugins, scan paths, progress), `externalPluginActivationStore.ts` (activation status and loaded instances).
- **`useCases/faustEngine/`**: Dynamic Faust DSP WebAssembly compiler and builtin effects (`compileFaustDSP.ts`, `builtinDSP.ts`).

## Invariants & Traps

- **A rejected state restore makes the runtime state non-authoritative**: when a plugin rejects its saved chunk at activation, the instance is marked as a failed restore here, and state capture must preserve the stored project chunk until authoritative state exists again. An explicit `setExternalPluginState` replacement pushes the new chunk to the host through `restorePluginState` and clears the marker only once the host accepts it; a rejected push keeps the marker standing so the next activation retries the replacement from project truth. Reading plugin state never clears the marker (Decision 0003). Only a restore whose activation is still current settles the marker: one a teardown overtook (a removal admitted while the first load was in flight queues its unload ahead of the load's restore), or whose id a newer activation now holds, answers superseded and writes no marker, status or carry change, because its outcome no longer describes the loaded instance. A graph rebuild or session retirement is not such a teardown: it ends the graph generation but waits on the activation with the instance still loaded, so a project-chunk restore or retry settles the marker the rebuild's live-state read then honours, and a rejected chunk is never carried as the plugin's defaults; a carried restore it overtook answers superseded and keeps its carry, which the rebuild's read carries forward in place of the plugin's state.
- **Capture authority belongs to one native instance generation**: project Save/Export reads through `readExternalPluginStateForCapture`, whose opaque token is invalidated at load, restore, keyed/unkeyed unload, restore settlement, instance forgetting, graph rebuild, session retirement, and whole-runtime clear admission. A caller may accept bytes only while that receipt remains current through its Command commit; a reused string instance id never revives an old receipt. A read that fails on a loaded instance with no pending or failed restore answers `unreadable` with the current token, never a preserve: the stored chunk may lack the instance's edits, so Save and Export must report it.
- **The restore-failure warning is once per failure episode**: `shouldWarnExternalPluginRestoreFailure` records the instance as warned, and every marker-resolve site (restore success, replacement acceptance, unload, graph teardown) drops the warned entry with the marker. A new resolve site must clear both sets or resolved-then-refailed instances stay silently unwarned.
- **Live state crosses an app-initiated teardown through the carry store, never the document**: the removal unload (`unloadPluginCarryingLiveState`, which a created track's Undo also uses), the graph-repair unload, the engine retire, the project-switch unload (`unloadPluginsBeforeProjectSwitch`) and the session-retirement unload (`beginProjectSessionPluginRetirement`'s `retire`) read each instance's live state first, and commit it to `carriedExternalPluginStates` only for the instances actually torn down. The next activation of the same instance id and plugin consumes it once in place of the project chunk; an activation issued while a keyed unload of that instance id is still pending waits for that unload to settle and then activates afresh, so it consumes the carry rather than answering from the instance the unload is about to destroy, unless a later keyed unload of that instance id or a runtime rebuild was admitted while it waited, in which case it answers superseded without loading (Remove, Undo, Redo); that wait is bounded (`PENDING_UNLOAD_WAIT_TIMEOUT_MS`) because callers await activation inside committed actions, and an unload still pending at the deadline fails the activation without loading and leaves the instance to the unload, and if that unload then rejects, the still-loaded instance's slot shows that instance as it then stands (its restore failure, else whether the engine has taken it), unless another writer replaced the timeout error meanwhile; a read that fails or times out (`TEARDOWN_STATE_READ_TIMEOUT_MS`) warns the user by plugin name, and the instance comes back with its saved state. The read is bounded inside the instance's lifecycle turn as well as at the caller, because the native control-gate wait runs to its own deadline and a hung read never answers: the deadline releases the read and its lifecycle turn for later TypeScript operations and a rebuild. A plugin hung inside its own native call, whether or not the engine has attached it, holds the native control gate until the gate deadline (`CONTROL_GATE_DEADLINE`), after which the native host treats the instance as unresponsive: it stops processing, and while that call still holds the gate every later control call on it refuses at once with the `plugin-unresponsive:` refusal (`isPluginUnresponsiveFailure`). The verdict is not final, because a slow call cannot be told from a hung one: the slow call letting go of the gate withdraws it, and the instance processes again with no further control call. An unload or retire detaches an unresponsive instance from the engine and the instance map but leaves it allocated in the retirement vec until the hung call releases its reference, because nothing can stop that call and freeing memory it runs in is undefined behaviour. A rebuild fence (graph repair or session retirement) waits for the operations admitted before it for at most `LIFECYCLE_SETTLEMENT_DEADLINE_MS`, sized above the native gate deadline so a natively queued call answers first; an operation still pending then is let go, its lifecycle turn is released, its pending keyed unload admitted before the fence is let go too so a reactivation loads afresh instead of waiting, and neither that unload nor any earlier one admitted for the id starts once let go or writes onto the id's record when its native call answers late (no forget, no attachment restore), and its carry commit discards the removal's read only when a later activation took the id after that read started, because the id may already belong to a later activation; a late refusal still rejects to the caller and keeps the removal's carry out, while a keyed unload scheduled during the fence still owns the instance and is waited for, and its slot is failed with the unresponsive message and the user told by plugin name (`failUnresponsiveExternalPlugins`). The project-switch unload runs before the replacement is certain, so it keeps the outgoing project's carries, removal carries included: a refused or superseded replacement rebuilds the outgoing graph from them, and only then warns about the reads it lost, while the authority switch itself drops every carry in its own synchronous turn (`settleProjectSwitchPluginTeardown`), since persisted instance ids return with the next project; its read waits on each instance's lifecycle turn, so a hung plugin can add up to the read deadline to a project switch. The session-retirement unload runs before a window close or quit is certain, so it keeps the project's carries the same way: a cancelled quiesce (`reopen`) rebuilds the graph from them and only then warns about the reads it lost, and only a session that really ended (`release`, after the window is destroyed) drops every carry, silently; its reads run inside the retirement's own rebuild fence, so quit gains at most the read deadline and never waits without bound. Every other whole-runtime unload (a load whose document already switched, through the unkeyed `unloadPlugin()`) drops the carries too; a commit whose read batch started before a drop is discarded, and so is the read of any instance whose carry was written or rejected, or that was activated again, after that read started, because a newer owner of that instance id already decided its carry, though a torn-down instance still loaded without a current read warns, since its live state was destroyed unread. Quit reads plugin state only within that bounded batch.
- **Native scan root security**: Plugin scanner enforces strict platform scan roots (macOS, Windows, Linux default directories). Custom roots require native authorization; symlinks and symlinked ancestor directories are rejected to prevent path traversal.
- **No leaked native handles**: Raw library handles, plugin pointers, and OS window handles stay behind the native desktop boundary; only serializable DTOs and instance IDs cross IPC.
- **Faust synchronization**: Faust is wired in PluginHost and AudioEngine; updates to Faust DSP types or node interfaces must remain synchronized across both modules.
- **External plugins are engine-hosted**: the native engine processes a hosted plugin inline on its own audio callback. No command carries per-block audio across the desktop IPC boundary, and the Web Audio graph holds a unity pass-through where such a device sits.
- **Released strips report back through the sink**: an unload's own chain release changes native strip state with no batch of its own, so `unloadPlugin` forwards the strips it released to whatever `registerReleasedStripReportSink` wired up, and the composition root — never this module — decides who that is.
- **External plugin parameter and tail stores are read-only outside the module**: `externalPluginParameterStore` and `externalPluginTailStore` are exported for reading; their writers stay off the `stores/index.ts` barrel. A reset, an unload or an activation seed retires every parameter re-read issued before it, so a late host answer never lands on a re-activated instance that reuses the id. A tail is kept in frames of the activation rate, never converted here, because both formats' infinite sentinel would not survive a conversion. The load seeds it, and every later figure carries the native host's sequence, one counter the host takes inside the instance's control gate for both `plugin-tail-changed` events and `read_plugin_tails` answers, so a larger sequence was read later however late it arrived. `plugin-tail-changed` revises a held instance's only, and an event or answer whose sequence is at or below the highest applied is ignored. `refreshExternalPluginTails` re-reads every held instance from the native host (VST3 raises no change event, so an export asks when it needs the figure) and publishes each answer by that sequence rule unless a seed, an unload or reload of that id, or a graph rebuild landed after the read was issued; an answer for an instance whose load has not seeded yet is held, like a change, and applied after the seed (the load carries no sequence, so a held figure always wins over the load's own, which the host read first). An instance the host could not reach is read once more after a short pause and otherwise keeps its stored tail, and a read that gets no answer within its bounded wait reports a timeout, which is not retried. Forgetting an instance drops its stamp and sequence once no read for it is in flight, and ending the graph generation drops every tail. A change for an instance whose load has not returned is held and wins over the load's own figure, because the native host attaches the instance and drains the change once before that answer arrives.
- **An out-of-service instance shows on its slot, and only the watcher that wrote it clears it**: `plugin-service-changed` carries the reason the native host stopped serving a loaded instance (a refused start of processing, or a VST3 bus layout it cannot route), or null once it is back. `watchExternalPluginService` writes `{ status: 'active', message }` — the slot's degraded rendering, which keeps the editor openable so the cause can be undone, never `error` — remembers that message per instance, writes only over a healthy slot or one already holding that message (a failed restore or the no-engine note stays), is not erased by the activation's own plain `active` write (the remembered message is kept), and on back in service resets the entry only if it still holds exactly that message. The remembered message leaves with the instance and with the graph generation.
